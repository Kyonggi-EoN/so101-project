# 핸드폰으로 SO-101 조종하기 (시뮬레이션)

> 안드로이드 핸드폰을 들고 움직이면 시뮬레이션 속 SO-101 로봇팔이 그대로 따라 움직인다.

**만든 사람** jsjin7371 · **기간** 2026-10-02 ~ · **상태** 진행 중 (시뮬레이션 완료, 실제 로봇 연결 전)

---

## 1. 무엇을 하는가 or 결과는 무엇인가

핸드폰 화면을 **누르고 있는 동안만** 핸드폰의 움직임이 로봇 그리퍼로 전달된다. 손을 떼면 로봇은 그 자리에 멈춘다 (클러치).

| 핸드폰 동작 | 로봇 반응 |
|---|---|
| 앞뒤 · 좌우 · 위아래로 이동 | 그리퍼가 같은 방향으로 이동 (손 이동량 × 0.4) |
| 평평하게 든 채 옆으로 돌리기 | 팔 전체가 좌우로 회전 (±90°) |
| 앞으로 숙이기 | 그리퍼가 숙여짐 (위로 30° ~ 아래로 90°) |
| 양옆으로 기울이기 | 그리퍼가 비틀림 (±90°) |

- **마우스처럼 쓴다.** 손을 뗐다가 다시 누르면 그 자리에서 이어서 움직인다. 누르는 순간 핸드폰이 향한 쪽이 "앞"이 된다.
- **안전 장치**: 작업 공간 제한(바닥 5cm 위, 베이스 뒤쪽 금지, 팔이 닿는 거리의 90%까지), 한 프레임 최대 5cm, 관절 속도 최대 2 rad/s
- 실제 로봇 없이 브라우저 3D 화면(meshcat)으로 확인한다. 핸드폰이 없으면 키보드 모드로 테스트할 수 있다.

사진·영상은 추가 예정.


## 2. 왜 만들었나

리더 암 같은 장비 없이 **핸드폰 하나로 로봇팔을 원격 조종(텔레오퍼레이션)** 하고 싶었다. 핸드폰은 카메라와 IMU 로 자기 위치·방향을 계산할 수 있으니(ARCore/WebXR), 이걸 로봇 그리퍼의 목표 자세로 쓰면 된다.

lerobot 에 핸드폰 → SO-100 예제가 있지만, 핵심 계산(기준 자세 + 변화량)이 파이프라인 안에 숨어 있어 고치기 어려웠다. 그래서 하드웨어 입력(`Phone`)만 lerobot 것을 쓰고, 나머지는 placo IK 예제를 참고해 직접 짰다.

- **placo 를 직접 쓴 이유**: lerobot 의 `RobotKinematics` 는 목표 하나(frame task)만 쓰는 얇은 래퍼다. 정규화, 관절 속도 제한, 가중치 조절을 쓰려고 placo 를 직접 불렀다.
- **lerobot 파이프라인을 안 쓴 이유**: `EEReferenceAndDelta` 를 파이프라인 밖에서 부르면 `ValueError: Transition is not set`. 직접 구현하는 쪽이 더 단순했다.
- **시뮬레이션 먼저**: 실제 로봇에 연결하기 전에 안전 장치와 조작감을 확인하려고.


## 3. 실행 방법

**준비물**

- 리눅스 PC (우분투에서 확인함). 로봇팔은 **필요 없다** (시뮬레이션만)
- 핸드폰 모드: ARCore 를 지원하는 Android 핸드폰 + PC 와 **같은 네트워크** (같은 Wi-Fi, 또는 둘 다 Tailscale)
- 키보드 모드: 핸드폰 없이 키보드로 테스트

**설치** (리포 루트에서, 처음 한 번)

```bash
uv sync --extra placo-dep --extra phone
```

- `placo-dep` = IK(관절 각도 계산)·3D 화면, `phone` = 핸드폰 연결
- 그냥 `uv sync` 만 하면 위 두 개가 **다시 지워진다**. 항상 같이 붙인다

**실행 1 — 키보드 모드** (핸드폰 없이)

```bash
GLIBC_TUNABLES=glibc.rtld.execstack=2 uv run python projects/02-phone-teleop-viz/phone_teleop_viz.py --source keyboard
```

- 터미널 위쪽에 로그(목표·실제 위치)가 계속 갱신되고, 그 아래에서 명령을 입력한다
- 그래프로 보고 싶으면 끝에 `--log rerun` 을 붙인다 (로그가 터미널 대신 브라우저로 간다)
- 앞의 `GLIBC_TUNABLES=...` 는 꼭 붙인다. 없으면 `RuntimeError: HEBI Core library not found` (5번 참고)
- 실행하고 4~5초 기다린 뒤 터미널의 `>` 에 명령을 입력한다

| 명령 | 뜻 |
|---|---|
| `on` | 클러치 누르기 (이때부터 움직임이 반영된다) |
| `off` | 클러치 떼기 (로봇이 그 자리에 멈춘다) |
| `x0.1` | 앞으로 10cm (`x-0.1` 은 뒤로) |
| `y0.1` | 왼쪽으로 10cm (`y-0.1` 은 오른쪽) |
| `z0.05` | 위로 5cm (`z-0.05` 는 아래) |

예: `on` → `x-0.1` → `off`. 거리는 **누른 순간의 위치**부터 잰다. 이어서 움직이려면 `off` → `on` 후 다시 입력한다. 키보드는 위치만 움직이고, 배율 없이 1:1 이다.

**실행 2 — 핸드폰 모드**

```bash
GLIBC_TUNABLES=glibc.rtld.execstack=2 uv run python projects/02-phone-teleop-viz/phone_teleop_viz.py
```

1. 핸드폰 브라우저(Chrome)에서 `https://<PC IP>:4443` 접속
   - PC IP 확인: `ip -4 -br addr` → `192.168.0.x` 형태의 주소 (Tailscale 이면 `100.x.x.x`)
   - 예: `https://192.168.0.8:4443`
   - 인증서 경고가 뜨는 것은 정상 → "고급 → 계속 진행"
   - 접속이 안 되면 방화벽: `sudo ufw allow 4443/tcp`
2. 핸드폰을 **평평하게(화면이 위), 위쪽 끝을 로봇 앞쪽으로** 들고, **화면을 터치한 채 손가락을 살짝 움직인다** (캘리브레이션 = 지금 자세를 기준으로 잡기). 숙이기·기울이기 각도는 이 자세를 0° 로 잰다. 터미널에 `Touch and move on the WebXR page ...` 가 떠 있는 동안 기다리고 있는 것이다
3. 화면을 **터치하고 있는 동안만** 로봇이 핸드폰을 따라 움직인다. 조작법은 1번 표
4. 끝에 `--record` 를 붙이면 매 프레임 값이 `outputs/teleop_log.csv` 에 저장된다 (조작감 분석용)

**화면 주소**

| 화면 | 주소 |
|---|---|
| 3D 로봇 (meshcat) | `http://127.0.0.1:7000/static/` |
| 그래프 (rerun, `--log rerun` 일 때) | `http://localhost:9091/?url=rerun+http://127.0.0.1:9876/proxy` |

원격 접속(VS Code Remote-SSH)이면 포트 7000, 9091, 9876 을 포워딩한다.

**이렇게 나오면 성공** (키보드 모드에서 `on` → `x-0.1` 입력 후)

```
enabled            : True
gripper_vel        : +0.0
phone delta        : pos [-0.100 +0.000 +0.000]  rot [+0.000 +0.000 +0.000]
current robot pose : pos [+0.391 -0.000 +0.226]  rot [+0.038 +1.570 +0.038]
new robot pose     : pos [+0.291 -0.000 +0.226]  rot [+0.038 +1.570 +0.038]
actual robot pose  : pos [+0.291 -0.000 +0.226]  rot [+0.038 +1.570 +0.038]

on
> x-0.1
```

`new robot pose`(목표)와 `actual robot pose`(실제)가 같아지면 IK 가 목표에 도달한 것이다. 브라우저에서 meshcat 주소를 열면 로봇팔이 움직이는 것이 보인다.

**테스트** (핸드폰·로봇 없이, 각각 `OK: ...` 가 나오면 통과)

```bash
for t in test_arm_rotation test_orientation_clutch test_workspace_edge; do
  GLIBC_TUNABLES=glibc.rtld.execstack=2 uv run python projects/02-phone-teleop-viz/test_src/$t.py
done
```


## 4. 어떻게 동작하는가

매 프레임(30Hz) 이 순서로 계산한다.

```
핸드폰 (WebXR, :4443) ── lerobot Phone ──→ 핸드폰 자세 + 누름 여부
  ① OrientationClutch      누른 순간 핸드폰이 향한 쪽을 "앞" 으로
  ② phone_to_robot_action  핸드폰 축 → 로봇 축 (같음), 위치 × 0.4
  ③ PhoneToTargetPose      목표 = 누른 순간 그리퍼 자세 + 누른 뒤 변화량
                           (작업 공간·각도 범위 끝에서 넘친 양은 버림)
  ④ SafetyFilter           한 프레임 최대 5cm
  ⑤ IKSolver (placo)       목표 자세 → 관절 각도 (관절 한계, 속도 2 rad/s)
  ⑥ meshcat 3D 화면 + 로그 (terminal / rerun / CSV)

키보드 모드는 ③ 부터 같은 길로 간다 (KeyboardSource)
```

```
projects/02-phone-teleop-viz/
├─ README.md
├─ phone_teleop_viz.py             메인. 위 ①~⑥ 이 전부 여기 있다
├─ so101-description/              SO-101 URDF + 메시 (SO-ARM100 리포에서 가져옴)
├─ docs/                           설정 메모(docs.md), 참고 예제 분석
└─ test_src/
   ├─ keyboard_ik_viz.py           키보드 입력 소스
   ├─ debug_log.py                 rerun 그래프 로그 (--log rerun)
   ├─ csv_log.py                   CSV 녹화 (--record)
   ├─ phone_record.py              핸드폰 원본 값 녹화 (축 방향 확인용)
   ├─ frame_replay.py              리팩토링 전후를 프레임별로 비교
   ├─ test_arm_rotation.py         회전 매핑, 각도 범위
   ├─ test_orientation_clutch.py   방향 클러치, 축 매핑
   └─ test_workspace_edge.py       작업 공간 끝에서 멈추고 바로 되돌아오는지
```

**핵심 아이디어 세 가지**

- **클러치 = 마우스.** 마우스를 들어서 옮겨도 커서는 안 움직이는 것처럼, 손을 떼고 핸드폰을 옮겨도 로봇은 가만히 있다. 다시 누르면 그때의 그리퍼 자세에서 이어진다. 화면 끝에서 커서가 멈추듯, 작업 공간 끝에서는 로봇이 멈추고 넘친 손 이동량은 버린다 (되돌리면 바로 따라옴).
- **작업 공간 = 사람 어깨.** 어깨를 고정하고 팔을 휘두르면 손끝이 그리는 공이 최대 범위다. SO-101 의 어깨 관절(0.039, 0, 0.117)을 중심으로, 최대 도달 거리 0.41m 의 90% 인 0.37m 공 안으로 목표를 제한한다. 공으로 못 막는 바닥(z ≥ 5cm)과 베이스 뒤(x ≥ 0)는 상자로 막는다.
- **로봇이 할 수 있는 회전만 주문한다 = 책상 스탠드 조명.** SO-101 은 관절이 5개라서 손목을 좌우로 꺾는 관절이 없다. 그래서 "제자리에서 그리퍼만 옆을 봐" 는 불가능하다. 핸드폰을 옆으로 돌리면 스탠드 조명을 돌리듯 팔 전체가 돌게 하고, 숙이기·기울이기만 그리퍼에 준다.

IK 는 placo 의 soft frame task 하나(위치 가중치 0.5, 방향 가중치 0.01)에 아주 작은 정규화(1e-6)와 관절 속도 제한을 더해 푼다.


## 5. 막혔던 것과 해결 방법 ★

### hebi 라이브러리를 못 찾음

**에러**

```
RuntimeError: HEBI Core library not found
```

**원인** 진짜 원인은 그 위에 찍힌 `cannot enable executable stack`. glibc 2.41 부터 실행 가능한 스택을 요구하는 라이브러리를 막는다 (`ldd --version` 으로 확인).

**해결** 실행할 때 앞에 `GLIBC_TUNABLES=glibc.rtld.execstack=2` 를 붙인다. 스크립트 안에서 `os.environ` 으로 설정하면 효과가 없다 (라이브러리를 읽기 전에 정해져야 함).

### 핸드폰에서 접속이 안 됨

**에러**

```
This site can't be reached / ERR_CONNECTION_TIMED_OUT
```

**원인** 방화벽이 4443 포트를 막음 / 원격 작업 중이라 핸드폰과 PC 가 다른 네트워크.

**해결** `sudo ufw allow 4443/tcp`. 원격이면 핸드폰에도 Tailscale 을 켜고 `https://<PC 의 Tailscale IP>:4443`. WSL 이면 미러 모드 + Hyper-V 방화벽 규칙 (`docs/docs.md` 5장).

### placo 가 메시·프레임을 못 찾음

**에러**

```
ValueError: Mesh assets/... could not be found
RuntimeError: Frame with name so101_new_calib not found
```

**원인** placo 는 URDF 옆에 메시 파일(`assets/`)이 있어야 한다 (lerobot IK 는 URDF 하나로 됨). 프레임 이름은 URDF 파일 이름이 아니라 URDF 안의 링크 이름이다.

**해결** SO-ARM100 리포의 URDF 와 메시를 통째로 `so101-description/` 에 넣고, 그리퍼 프레임은 `gripper_frame_link` 로 쓴다.

### 핸드폰을 앞으로 밀었는데 로봇이 옆으로 감 (에러 없음)

**원인** lerobot 의 축 매핑(`x = -y, y = x`)이 우리가 드는 자세(평평하게, 위쪽 끝이 앞)와 90° 어긋남. 핸드폰 값은 이미 로봇과 같은 축(앞·왼쪽·위)으로 들어온다.

**해결** 핸드폰 값을 녹화해서(`test_src/phone_record.py`) 어느 축이 움직이는지 확인하고, 변환 없이 그대로 쓴다. 처음엔 녹화의 부호만 보고 반대로 넣었다가 실제로 움직여 보니 틀렸다. **녹화는 축만 믿고, 부호는 직접 움직여서 확인한다.**

### 작업 공간 끝에 닿은 뒤 손을 되돌려도 로봇이 안 움직임 (에러 없음)

**원인** 목표 = 기준 + 손 이동량 → 벽에서 자름. 자른 값은 다음 프레임에 안 쓰여서, 벽 밖으로 넘어간 손 이동량이 계속 남아 있었다. 손을 20cm 넘게 밀었으면 20cm 를 되돌려야 그때부터 움직였다.

**해결** 넘친 양을 따로 쌓아서 빼 준다. 마우스가 화면 끝에서 멈췄다가 반대로 움직이면 바로 따라오는 것과 같다 (`test_workspace_edge.py`).

### 핸드폰을 옆으로 돌렸는데 그리퍼가 비틀림 (에러 없음)

**원인** 회전을 `기준 @ 회전` (그리퍼 자기 축 기준)으로 곱했다. 시작 자세에서 그리퍼의 z 축은 월드의 "앞" 이라, 핸드폰의 z 축(위) 회전이 그리퍼의 "앞" 축 회전 = 비틀기가 됐다. 녹화로 확인한 핸드폰 회전축과 목표 회전축의 일치도(cos)는 옆으로 돌리기 −0.13, 기울이기 −0.15.

**해결** 핸드폰 회전을 (옆으로 돌리기, 숙이기, 기울이기) 세 각도로 나눠서 각각 로봇이 할 수 있는 동작(팔 전체 회전, 그리퍼 숙임, 그리퍼 비틀림)으로 바꿔 준다 (`test_arm_rotation.py`).

### 그리퍼 방향을 지키게 하면 손을 못 따라감 (에러 없음)

**원인** 관절이 5개라 위치 3개 + 방향 3개를 동시에 못 맞춘다. IK 의 방향 가중치를 키우면 방향을 지키느라 위치를 포기한다. 가상 핸드폰 시험(3cm 씩 3,347번)에서 덜 따라간 비율: 가중치 1.0 → 42.6%, 0.01 → 7.8%, 0 → 1.0%. 하지만 0 이면 손목 비틀림이 떠돌아서 3분 쓰면 48° 틀어졌다.

**해결** 가중치는 0.01 로 두고, 로봇이 물리적으로 할 수 없는 방향은 애초에 주문하지 않는다 (위 항목).

### 오래 쓰면 그리퍼가 하늘을 보고 조작이 이상해짐 (에러 없음)

**원인** 누를 때마다 지금 그리퍼 방향이 새 기준이 되고, 핸드폰 회전은 누른 뒤의 변화량이라 마우스처럼 **쌓인다**. 위치만 옮기려다 손목이 같이 5~10° 돈 것도 쌓였다. 녹화에서 그리퍼가 위로 83° 까지 갔고, 그때 관절이 한계에 붙어 있던 시간이 56%.

**해결** 위치와 같은 규칙으로 각도 범위(숙임 −30° ~ 90°, 비틀림 ±90°)를 두고, 넘친 양은 버린다. 나중에 옆으로 돌리기도 같은 규칙(±90°)으로 바꿨다: 전엔 범위가 없어서 많이 돌리면 그리퍼 끝이 베이스 뒤 벽(x=0)에 잘렸고, 잘린 양이 위치에 쌓여 되돌려도 원호에서 5cm 벗어났다.

### 핸드폰을 숙인 채 누르면 앞으로 밀어도 로봇이 위로 감 (에러 없음)

**원인** 방향 클러치가 누른 순간의 핸드폰 방향 **전체**(숙인 각도 포함)를 "앞" 으로 잡았다. 60° 숙인 채 앞으로 10cm 밀면 앞 5cm + 위 8.7cm 가 된다.

**해결** 옆으로 돌린 각도(yaw)만 기준으로 잡는다 (`test_orientation_clutch.py` 5번).

### 이것은 아직 모르겠다

- 같은 그리퍼 각도를 유지한 채 높이 들거나 멀리 뻗으면 손목(`wrist_flex` +95°)이 한계에 붙는다. 위치는 따라가서 지금은 두었지만, 팔을 뻗을 때 각도를 얼마나 양보하게 할지는 정하지 못했다.


## 6. 한계와 다음에 할 것

**지금 안 되는 것**

- **실제 로봇에서 확인 안 함.** 기구학 시뮬레이션이라 중력·충돌·모터 힘이 없다 (팔이 책상을 뚫어도 모른다)
- 그리퍼 열고 닫기가 연결 안 됨 (핸드폰 A/B 버튼 값 `gripper_vel` 은 읽기만 함)
- 베이스 바로 근처(베이스 회전축에서 수평 15cm 안쪽)는 팔을 그만큼 접을 수 없어서 덜 따라가거나 못 간다
- 목표와 실제가 계속 크게 벌어져도 멈추지 않는다 (오차 감시 없음)
- Android 만 확인했다. 캘리브레이션할 때 핸드폰을 평평하게 들어야 숙이기·기울이기 각도가 맞다

**다음에 하면 좋을 것**

- 실제 로봇 연결: 라디안 → 도 변환, `SO101Follower.send_action`, 기준 자세를 실제 관절값에서 읽기, 처음엔 배율·속도를 작게
- 그리퍼 열고 닫기 (lerobot `GripperVelocityToJoint` 참고)
- 오차 감시 → 정지 (물체에 막혀 계속 밀어붙이는 상황 방지)
- 베이스 근처를 막는 기둥 모양 벽, meshcat 에 작업 공간 표시
- MuJoCo 물리 시뮬레이션 (`so101-description/` 에 `scene.xml` 이 이미 있음)
- 정량 평가: 추종 오차, 지연, 물체 옮기기 성공률
